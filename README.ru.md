# foureyes

[![CI](https://github.com/dmitrykarpushkin/foureyes/actions/workflows/ci.yml/badge.svg)](https://github.com/dmitrykarpushkin/foureyes/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue)](LICENSE)

**Судья для ИИ-агентов, которые пишут код: кто сделал изменение, тот его не проверяет и не принимает.**

Для тех, кто пускает несколько агентов Claude Code или Codex работать в свои репозитории и хочет, чтобы «готово»
значило «проверил кто-то другой». Название — от принципа четырёх глаз из банков и аудита: свою операцию сам не
подтверждаешь.

![builder-1 пишет изменение, tester-1 его запускает, validator-1 проверяет коммит в main; попытка builder-1 проверить себя отклонена](docs/diagram.svg)

## Зачем

Слова агента «готово» — не доказательство. Агенты пишут, что тесты прошли, хотя их не запускали, сами одобряют свой
дифф и уходят за рамки задачи. Фраза «проверь свою работу» в промпте этого не лечит: промпт — это просьба. foureyes
выносит правила, которые должны соблюдаться всегда, в маленький движок, который просто не пропускает плохой шаг.

- **«Готово» проверяет другой.** Задача идёт по этапам: разбор, сборка, тест, приёмка, проверка. Если один и тот же агент
  пытается закрыть два этапа, которые должны закрывать разные агенты, команда завершается с кодом 1 и шаг не записывается.
- **Доказательство — коммит, а не фраза.** На приёмке и проверке нужно сослаться на настоящие коммиты в main: новее самой
  задачи и разные для двух этапов.
- **Ваше «да» привязано к тексту, который вы одобрили.** Одобрение хранит хеш текста задачи. Если текст потом поменяли,
  одобрение больше не действует.
- **Текст, который читает агент, остаётся данными.** Описание задачи передаётся агенту внутри метки со свежим случайным
  числом, поэтому поддельная строка «конец данных» внутри текста его не закроет.
- **Можно прочитать за вечер.** Около 500 строк на Python плюс PyYAML, ни одного вызова модели, 61 тест. Подходит любой
  инструмент для агентов, который умеет запускать команду в терминале.

## Как он отказывает

Из настоящего вывода `sh examples/walkthrough.sh`: скрипт проводит одну задачу через всю цепочку во временном
git-репозитории (сокращено, вместо id задачи — `ID`; полный вывод в [docs/walkthrough.md](docs/walkthrough.md)):

```console
$ lab.py done ID --agent scout-1 --verdict go --value 3 --cost-pct 0.5
refused: scout-1 is the submitter of this idea; the judge must differ
(exit 1)

$ lab.py done ID --agent builder-1 --verdict ok --note 'looks good to me'
refused: builder-1 already worked on stage build of this idea; the judge of test must differ
(exit 1)

$ lab.py done ID --agent applier-1 --verdict ok --evidence b610912
refused: --evidence is older than the idea (committed before submitted_at); it must be a new commit
(exit 1)

$ lab.py done ID --agent validator-1 --verdict ok --evidence 523cf1d
refused: validate evidence is the same commit as the apply evidence; they must differ
(exit 1)
```

По порядку: автор задачи пытается сам её разобрать; сборщик — сам себя протестировать; приёмщик приносит старый коммит;
проверяющий повторяет коммит приёмки. Потом скрипт руками правит сохранённый файл, чтобы сборщик стал своим же
тестировщиком, и отдельная проверка это ловит:
`event 4 (test) is by builder-1, who also worked on a stage it must differ from`.

## Чем отличается

foureyes не пишет спецификации и не запускает агентов. Он стоит между агентами, которые у вас уже работают, и следит,
кто что подписывает. Большие инструменты намного зрелее; foureyes лучше всего работает поверх них.

| Инструмент | В чём силён | Что добавляет foureyes | Когда выбрать его |
|---|---|---|---|
| [Spec Kit](https://github.com/github/spec-kit), [OpenSpec](https://github.com/Fission-AI/OpenSpec) | Помогают с агентом написать спецификацию, план и задачи; OpenSpec проверяет структуру документов | Отказ в коде, если автор сам оценивает свою работу или не приносит настоящий коммит | Нужна помощь в написании спецификации; foureyes может использовать любой из них для крупной задачи |
| [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD), [superpowers](https://github.com/obra/superpowers) | Целый процесс для агентов: роли, планирование, TDD, ревью описано в тексте навыков | Очередь задач между сессиями с историей; независимость проверяющего обеспечена кодом, а не просьбой | Работаете в одной сессии и не хотите ничего настраивать |
| [CrewAI](https://github.com/crewAIInc/crewAI), [LangGraph](https://github.com/langchain-ai/langgraph), [AutoGen](https://github.com/microsoft/autogen) | Запускают агентов: графы, состояние, память, инструменты | Судья, который не вызывает модель, а доказательством считает коммиты в git | Нужна среда для запуска агентов; foureyes нужен оркестратор снаружи |

## Быстрый старт

Unix (macOS, Linux), Python 3 с PyYAML, git. Проверено на Python 3.13.

```bash
git clone https://github.com/dmitrykarpushkin/foureyes && cd foureyes
pip install -r requirements.txt
sh examples/walkthrough.sh        # одна задача через всю цепочку, включая четыре отказа
```

`python3 -m unittest discover -s tests` запускает 61 тест. `bin/foureyes` — короткое имя для `python3 lab/lab.py`.

## Как устроено

- Каждая задача (в коде она называется idea) — один YAML-файл. Каждый шаг дописывается в конец, прошлое не переписывается.
- Этапы и правило «кто кого не может судить» лежат данными в `lab/chains.yaml`; `lab.py done` их соблюдает.
- Отдельная проверка перечитывает сохранённые файлы, так что ручную правку в обход правил видно и задним числом.
- Оркестратор спрашивает у `lab.py next`, что можно взять, запускает на каждый этап нового агента с текстом
  `lab.py brief ID`, и этот агент закрывает свой этап через `lab.py done ID --agent СВОЙ_ID`.
- Сам процесс — размеры задач, план как список проверяемых критериев, что значит «готово» — описан в
  [docs/SPEC.md](docs/SPEC.md) (на английском).

Подробнее (на английском): [как устроено](docs/how-it-works.md) · [спецификация](docs/SPEC.md) ·
[полный прогон](docs/walkthrough.md) · [эвалы из логов агентов](lab/evals/README.md)

## Статус и ограничения

Личный исследовательский проект: им пользуется один человек, чтобы управлять своими агентами. Честно:

- **id агента — просто метка.** Движок сравнивает имена из `--agent` и не может доказать, что за двумя именами стоят два
  свежих агента. Запускать нового агента на каждый этап — работа оркестратора.
- **Не измерено:** снижает ли разделение автора и проверяющего число ошибок по сравнению с самопроверкой и как часто
  проверяющий пропускает проблему.
- **Наблюдение из закрытого проекта, откуда это взято:** через движок прошло 212 задач; 145 отброшены (141 — на разборе),
  36 прошли все семь этапов. Все их вели агенты одной и той же системы, так что это показывает, что цепочка работает
  механически, а не что решения были верными. Из этого репозитория это не воспроизвести.
- Одобрение проверяет только форму ссылки, а не кто её написал; метка против подмены инструкций снижает риск, но её
  успешность не измерялась.

## Откуда это

Выделено 2026-10-26 из моего закрытого монорепозитория, где это работало на моих собственных проектах. В нём 1001 коммит
с 2026-09-28 по 2026-10-26; 105 из них касаются движка и спецификации. Большую часть коммитов сделали агенты, работавшие
под этими проверками. В закрытой истории есть другие проекты и внутренние id, поэтому она не публикуется; что и когда
менялось — в [CHANGELOG.md](CHANGELOG.md).
